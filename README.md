# کابینت — دستیار آشپزخانه

برنامه فارسی و راست‌به‌چپ برای موجودی خانه، پیشنهاد غذا، برنامه وعده‌ها و خرید مواد غذایی. منطق محاسبات از رابط جداست و مسیر اصلی محصول قابل اجراست.

## اجرای محلی

نیازمندی: Node.js 22.12 یا جدیدتر، npm و یک مرورگر جدید.

```powershell
npm ci
npm run dev -- --port 3017
```

نشانی: http://127.0.0.1:3017

بدون تنظیم Supabase، برنامه با **حالت آزمایشی مشخص** باز می‌شود. داده آن در `localStorage` همان مرورگر است؛ حساب واقعی یا ذخیره ابری محسوب نمی‌شود. از تنظیمات می‌توانید آشپزخانه آزمایشی را خالی کنید. داده نمونه هیچ‌گاه در خانوار واقعی درج نمی‌شود.

## اتصال حساب واقعی به Supabase

1. یک پروژه Supabase ایجاد کنید.
2. فایل `supabase/migrations/202610090001_initial.sql` را در SQL Editor اجرا کنید.
3. فایل `supabase/seed.sql` را اجرا کنید. این فایل فقط کاتالوگ مواد و غذاهاست.
4. `.env.example` را با نام `.env.local` کپی و مقدارهای زیر را تنظیم کنید:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR-PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR-PUBLISHABLE-KEY
SUPABASE_SERVICE_ROLE_KEY=YOUR-SERVER-ONLY-KEY
```

5. در تنظیمات Auth، ورود ایمیل/رمز را فعال و URL سایت و `/auth/callback` را در فهرست Redirect URL قرار دهید؛ برای محلی `http://127.0.0.1:3017/auth/callback`.
6. برنامه را دوباره اجرا کنید. اگر قبلاً حالت آزمایشی باز بوده، «خروج از حالت آزمایشی» را بزنید. ثبت‌نام کنید و در صورت فعال بودن تأیید ایمیل، لینک آن را در همان مرورگر باز کنید.

کلید `service_role` فقط در محیط سرور قرار می‌گیرد؛ متغیر `NEXT_PUBLIC` نیست. خواندن داده با هویت کاربر و RLS انجام می‌شود. عملیات تغییر پس از احراز هویت و بررسی نقش، از RPC اختصاصی سرور اجرا می‌شود.

### تعیین مدیر کاتالوگ

پس از ایجاد حساب مدیر، شناسه او را از Auth بردارید و توسط مدیر پایگاه داده اجرا کنید:

```sql
insert into public.catalog_admins(user_id)
values ('ADMIN-USER-UUID');
```

حالا `/admin` برای این حساب فعال است. مدیر می‌تواند مواد، مقدارها، مراحل، تصویر HTTPS و وضعیت انتشار غذا را تغییر دهد. نسخه قبلی وعده‌های ثبت‌شده حفظ می‌شود. تصاویر می‌توانند از Supabase Storage یا میزبان HTTPS مجاز خودتان ارائه شوند؛ آپلود مستقیم تصویر در این نسخه اضافه نشده است.

## وضعیت غذاهای اولیه

۱۰ پروفایل در `src/data/catalog.json` وجود دارد: ۷ غذا منتشرشده و ۳ پیش‌نویس. لینک ماکارونی شکل‌دار، ماکارونی رشته‌ای و عدس‌پلو با سویا هنگام بررسی قابل بازیابی نبودند؛ داده این سه، پیش‌نویس تحریریه است و در پیشنهاد/برنامه کاربران عادی ظاهر نمی‌شود.

تبدیل مواد «عددی»، پیمانه و قاشق به گرم، زمان کل و تعداد نفراتِ درج‌نشده، تخمین اولیه هستند و در پروفایل و جزئیات غذا علامت دارند. این تخمین‌ها داده اندازه‌گیری‌شده منبع نیستند و مدیر یا کاربر باید آن‌ها را با مصرف واقعی اصلاح کند. متن مراحل بازنویسی کوتاه است؛ نشانی منبع حفظ شده است. تصویرهای فعلی SVG تصویرسازی برنامه هستند؛ عکس کاله دریافت یا بازنشر نشده است.

برای بازتولید seed از داده کاتالوگ:

```powershell
npm run seed:generate
```

این seed برای نصب اولیه است. به‌روزرسانی کاتالوگ فعال از پنل مدیر انجام شود؛ اجرای دوباره seed نسخه فعلی را جایگزین نمی‌کند.

## یادآوری سمت سرور و Web Push

بدون مرورگر باز، زمان‌بندی باید روی سرور اجرا شود. برای ارسال به دستگاه:

1. زوج کلید VAPID بسازید:

```powershell
npx web-push generate-vapid-keys
```

2. متغیرهای `NEXT_PUBLIC_VAPID_PUBLIC_KEY`، `VAPID_PRIVATE_KEY`، `VAPID_SUBJECT` و `CRON_SECRET` را تنظیم کنید. راز Cron باید حداقل ۳۲ نویسه تصادفی باشد.
3. برنامه را روی HTTPS مستقر کنید؛ محیط localhost برای آزمون Service Worker قابل استفاده است.
4. کاربر در تنظیمات، اعلان دستگاه را با اجازه مرورگر فعال کند.
5. مسیر `POST /api/cron/reminders` را هر دقیقه، با `Authorization: Bearer YOUR_CRON_SECRET` از زمان‌بند مطمئن فراخوانی کنید.

نمونه Supabase Cron پس از فعال‌کردن `pg_cron` و `pg_net` و ثبت رازها در Vault:

```sql
select cron.schedule('cabinet-reminders', '* * * * *', $$
  select net.http_post(
    url := (select decrypted_secret from vault.decrypted_secrets where name='cabinet_app_url') || '/api/cron/reminders',
    headers := jsonb_build_object(
      'Content-Type','application/json',
      'Authorization','Bearer ' || (select decrypted_secret from vault.decrypted_secrets where name='cabinet_cron_secret')
    ),
    body := '{}'::jsonb
  );
$$);
```

برای هر یادآوری/روز/ساعت، اعلان یکتا ساخته می‌شود. صف ارسال دارای قفل، وضعیت و حداکثر ۳ تلاش است. اشتراک منقضی حذف می‌شود. Push تحویل صددرصدی ندارد؛ وضعیت ارسال در `notification_deliveries` ثبت می‌شود و صندوق داخل برنامه مستقل از Push باقی می‌ماند. سرویس‌های Push شناخته‌شده Chrome، Firefox، Edge و Safari مجاز هستند.

حالت آزمایشی زمان‌بند سرور ندارد. دکمه «بررسی یادآوری‌ها اکنون» موعدهای همان روز را بررسی می‌کند و در صورت نیاز اعلان داخل برنامه ایجاد می‌کند.

## آزمون و ساخت

```powershell
npm run typecheck
npm test
npm run build
npm run test:e2e
```

آزمون‌های PostgreSQL از PGlite، موتور PostgreSQL درون‌حافظه‌ای، و شبیه‌سازی نقش‌های Supabase استفاده می‌کنند؛ اتصال خارجی لازم نیست. آزمون مرورگر روی پورت اختصاصی ۳۰۱۷ اجرا می‌شود و به Chrome نصب‌شده نیاز دارد. برای استفاده از Chromium همراه Playwright، `channel: 'chrome'` را از تنظیمات بردارید و `npx playwright install chromium` اجرا کنید.

آزمون مرورگر مسیر موجودی ← انتخاب غذا ← کمبود ← خرید ← پخت ← برگشت مصرف، ماندگاری داده آزمایشی، نسخه‌بندی غذا و نمایش موبایل را پوشش می‌دهد. آزمون ورود ایمیلی و ارسال Push واقعی باید پس از تنظیم سرویس‌های خارجی در محیط staging اجرا شود.

## استقرار

برنامه روی میزبانی دارای Node.js و پشتیبانی Next.js قابل استقرار است. متغیرهای محیطی را در میزبان تنظیم کنید، مهاجرت و seed را روی پروژه مقصد اجرا کنید و سپس `npm ci` و `npm run build` اجرا شوند. اجرای مستقل:

```powershell
npm run start -- --port 3017
```

اسکریپت محلی فقط روی loopback گوش می‌دهد. برای میزبانی کانتینر/سرور از `npx next start --hostname 0.0.0.0 --port 3000` پشت HTTPS استفاده کنید. Supabase Auth URLها و زمان‌بند را مطابق دامنه مقصد تنظیم کنید. کلیدهای عمومی Next.js در زمان build درج می‌شوند؛ پس از تغییر آن‌ها باید دوباره build کنید.

این مخزن سرویس خارجی ایجاد یا سایت را منتشر نمی‌کند. برای کاربری واقعی، اتصال Supabase و فعال‌سازی زمان‌بند ضروری است.

## محدودیت‌های نسخه فعلی

- هر حساب یک خانوار فعال دارد؛ اشتراک‌گذاری و دعوت حساب دوم هنوز رابط کاربری ندارد.
- بودجه و الگوی آشپزی ذخیره می‌شوند؛ رتبه‌بندی قیمت بدون داده قیمت معتبر اجرا نمی‌شود.
- کاربر می‌تواند مصرف واقعی را اصلاح کند؛ برآورد مصرف با حداقل ۳ ثبت معتبر و بازه حداقل ۷ روز، اطمینان متوسط می‌گیرد.
- برای آفلاین واقعی، صف همگام‌سازی وجود ندارد؛ تغییر حساب واقعی بدون اتصال ثبت موفق نشان داده نمی‌شود.
- مواد اختیاری در نیاز خرید و بررسی حساسیت محافظه‌کارانه لحاظ می‌شوند؛ مقدار مصرف آن‌ها می‌تواند صفر شود.
- مدل فعلی یک aggregate نسخه‌دار و projectionهای رابطه‌ای دارد. هر تغییر، aggregate خانوار را اتمی ذخیره می‌کند؛ برای سوابق طولانی و خانوارهای بزرگ، باید عملیات جزئی و آرشیو تاریخچه اضافه شود.
- حذف حساب مالک، خانوار تحت مالکیت و داده‌های آن را نیز حذف می‌کند؛ تأیید صریح داخل برنامه لازم است.

جزئیات معماری و قواعد در [docs/architecture.md](docs/architecture.md) آمده‌اند.

# نسخهٔ اولیه روی GitHub Pages

این نسخه بدون سرور، حساب کاربری و پایگاه داده اجرا می‌شود. موجودی، برنامهٔ غذایی، خرید و ویرایش آزمایشی دستورها در مرورگر همان دستگاه ذخیره می‌شوند؛ تغییرات بخش میزبان در این حالت فقط برای همان مرورگر هستند.

برای ساخت خروجی: `npm run build:pages`. فایل‌های آمادهٔ انتشار در `.pages-build/out` ساخته می‌شوند. این دستور یک کپی مخصوص انتشار می‌سازد و مسیرهای سرور را از آن کنار می‌گذارد؛ تنظیمات اتصال پایگاه داده در خروجی Pages خالی هستند.

در مخزن گیت‌هاب، بخش Settings → Pages، گزینهٔ Source را روی GitHub Actions قرار دهید. گردش‌کار `.github/workflows/pages.yml` با هر ارسال به `main` سایت را می‌سازد و منتشر می‌کند. آدرس این مخزن: `https://ShahramMinaei.github.io/Cabinet/`.

مخزن خصوصی برای Pages به پلن سازگار گیت‌هاب نیاز دارد؛ در حساب رایگان باید مخزن عمومی باشد.
